# Эффективное освобождение места в SpotlessMac

Дата: 2026-10-01. Основание: пользователь согласовал разбор места, расширение очистки,
общий размер приложений, доработку Docker и честный отчёт результата; запросил план.
Этот документ фиксирует решения для плана, а не разрешение на очистку текущего Mac.

## Цель и границы

Пользователь должен увидеть реальные источники занятого места, отличить восстанавливаемые
данные от личных и выбрать конкретные объекты для удаления. Нельзя считать весь объём
«Системных данных» мусором или обещать освободить его целиком.

macOS 14 minimum; Xcode 16.2; Swift 6 strict concurrency.
No third-party dependencies.
Сканирование и вычисление размеров выполняются вне MainActor; UI использует Observation.
Сканирование ограничено явными разрешёнными корнями, без полного обхода диска.
Файловое удаление использует только FileManager.trashItem, после предпросмотра и проверки SafetyRules.
Не трогать /System, /private/var/vm, /dev, /cores.
Сохранить Debug bypass лицензии; в Release проверять лицензию.
Не запускать реальную очистку пользовательского Mac при разработке и проверке.

## Что уже существует

- ScanEngine: пользовательские кэши, логи, DerivedData/CoreSimulator Caches,
  старые установщики и файлы от 500 МиБ в стандартных пользовательских папках.
- DiskOverviewView/DiskUsageView: обзор диска, крупнейшие домашние папки и drill-down.
  FolderSizeCalculator пропускает скрытые файлы и суммирует логические размеры.
- DiskSpaceService считает «Системой» остаток после /Applications и ~/Documents.
  Это не категория macOS; ~/Applications и другие документы не учтены отдельно.
- UninstallEngine находит приложение и кандидатов остатков; списка общих размеров
  приложений нет. Точное совпадение имени не означает, что данные являются кэшем.
- DockerClient/DockerCleanupView уже реализуют scan, точечное удаление,
  закрепление context/builder, повторную проверку и отдельное подтверждение томов.
  Существующую реализацию и тесты переиспользовать, не создавать второй клиент.

## Наблюдения, определяющие приоритет

Проверка размеров 2026-10-01, округление в ГиБ: Docker 64,7; Hugging Face cache 22;
Wooffoow recordings 19,3; AnythingLLM storage 16,8; Cursor 13,7; Claude 9,9;
MyProjects 31. Эти значения — измеренный объём, не гарантированная экономия.
Суммы вложенных папок нельзя складывать с их родителями. Категории macOS не имеют
однозначного соответствия путям. Снимков Time Machine команда tmutil не показала.

## Пользовательский поток

Вкладка «Диск» показывает ёмкость, свободное место и измеренные источники: программы,
данные приложений, документы/проекты, модели/кэши, прочее. Если измерение неполное,
показывает это явно. Остаток называется «Прочее и неразобранное», не «Система».

Пользователь открывает источник, видит его дочерние папки, размеры, полный путь,
статус доступа и объяснение. Доступные действия: открыть/показать в Finder,
перейти к деинсталлятору или Docker, либо выбрать поддерживаемый объект очистки.
Отдельные большие папки обнаруживаются даже без отдельных файлов от 500 МиБ.

Новые кандидаты по умолчанию не выбраны. Признаки: «Кэш, создаётся заново»,
«Потребуется повторная загрузка», «Личные данные», «Только просмотр».
Размер и возраст не являются доказательством ненужности.

## Политики источников

| Источник | Действие первой версии |
|---|---|
| ~/Library/Caches и существующие dev-кэши | Существующая очистка с предпросмотром |
| Cursor/Claude внутри Application Support | Только конкретные Cache/Code Cache/CachedData/CachedExtensionVSIXs после проверки каталога правил; User, WebStorage, vm_bundles, истории — просмотр |
| ~/.cache/huggingface/hub | Выбор целого репозитория модели/датасета со всеми его blobs; snapshots отдельно не удалять |
| ~/.cache/uv, ~/.npm/_cacache | Выбор известных кэшей после остановки соответствующих процессов; остальная папка .npm не считается кэшем |
| ~/.ollama/models | Показать модели/размер и открыть Ollama; файловое удаление не добавлять |
| ~/MyProjects | Поиск node_modules и проверяемых каталогов сборки, ручной выбор; исходники, .git, локальные БД, .env, vendor — не кандидаты |
| Wooffoow recordings | Отдельные записи после просмотра; каталог recordings целиком не выбирать |
| AnythingLLM storage, Cursor/User, Claude/vm_bundles | Просмотр и объяснение; неизвестное содержимое не удалять автоматически |
| Xcode/iOS DeviceSupport, CoreSimulator devices, JetBrains старых версий | Просмотр; не включать в существующую автоматическую очистку dev-кэшей |
| Docker | Переход к существующей точечной очистке через Docker CLI |

Application Support/Containers/Group Containers — явные корни просмотра.
Их добавление в просмотр не даёт разрешения на произвольное файловое удаление.
Для очистки whitelist расширяется только конкретными каталогами известных кэшей,
репозиториями Hugging Face и проверенными кандидатами внутри выбранных проектов.
При настройке HF_HOME/HF_HUB_CACHE нестандартный путь сначала явно выбирается пользователем;
значения конфигурации сами по себе не разрешают сканирование произвольного пути.

## Архитектура и безопасность

Отдельный StorageAnalysisEngine actor обслуживает существующую вкладку «Диск».
StorageSourceCatalog описывает read roots и известные действия; SafetyRules отдельно
проверяет право удаления. Единый PathPolicy проверяет канонический путь и границы
компонентов, симлинки не ведут обход за пределы разрешённого корня.

Измерение хранит logicalBytes и allocatedBytes, ошибки доступа и статус partial.
Рекурсивный обход ограничивает параллелизм до четырёх работников, поддерживает отмену,
не следует симлинкам, не загружает облачные placeholder-файлы. Hard links учитываются
один раз; разделяемые APFS extents не позволяют гарантировать будущую экономию.
Каталоги пакетов .app/фотобиблиотеки представлены единым объектом для действий.

CleanupPolicy не зависит только от ScanCategory: риск и действие определяются для
конкретного объекта. Перед каждым trashItem повторно проверяются whitelist, тип,
идентичность объекта и отсутствие симлинка; при изменении — отказ с повторным сканированием.
План удаления устраняет дубликаты и пересечение родитель/потомок.
Блокировать известное запущенное приложение; при невозможности установить активность
для нового кэша — не удалять, объяснить необходимость закрытия приложения/инструмента.
Не обещать полной защиты от внешних изменений файловой системы между проверкой и вызовом API.

Деинсталлятор раздельно показывает программу, кэш и личные данные. Сопоставление
по bundle ID/проверенному каталогу даёт подтверждённого владельца; сходство имён —
кандидат без автоматического выбора. Общие контейнеры не приписываются одному владельцу.
Личные данные не выбираются по умолчанию даже при точном совпадении.

Docker сохраняет собственную границу команд: без shell, общих prune, force удаления
используемых ресурсов и файлового удаления Docker.raw. Удаление через CLI необратимо,
это существующее исключение из Trash-only, описанное в спецификации Docker от 2026-09-18.
Нельзя расширять его на Ollama/другие инструменты без отдельного решения.

## Результат

После файловой операции показывать «Перемещено в Корзину: …»; Корзина продолжает
занимать место. Показать отдельно изменение свободного места на том же томе до/после,
с временем измерений и оговоркой об активности других процессов. Не очищать Корзину.
После Docker показывать удалённые ресурсы, ошибки, размер виртуального диска на диске
и отдельное измерение свободного места Mac. Не суммировать размеры слоёв образов как
гарантированную экономию; не запускать privileged reclaim helper автоматически.

## Приёмка

1. Анализ находит известные крупные источники, включая скрытые ~/.cache и ~/MyProjects.
2. Неполный доступ отличается от пустой папки; обзор не выдаёт остаток за размер macOS.
3. Личные данные/модели/новые кандидаты не попадают в массовую очистку автоматически.
4. За пределами разрешённых путей ничего не сканируется и не удаляется.
5. Программа+данные+кэш считаются без дублирования кандидатов/общих контейнеров.
6. Docker использует существующие защиты и показывает измеренный результат.
7. Проверки проходят на временных fixtures и fake исполнителях; реальный Mac не очищается.

## Очерёдность выпуска

A: точный отчёт и разбор источников (задачи 1–3).
B: известные кэши, модели, проекты и записи (задачи 4–5).
C: общий размер приложений и доработка Docker (задачи 6–7).
После каждого этапа — рабочая сборка; общая проверка — задача 8.
